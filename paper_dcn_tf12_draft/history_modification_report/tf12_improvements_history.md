## 2. 一页摘要

如果用一句话概括，这项工作的核心演进不是“把 baseline 的参数重新调了一遍”，而是把原始 Adaptive Koopman 的单体鲁棒控制思想，扩展成了一套可用于四车刚性载荷协同运输、并能在通信退化条件下保持可用性的完整控制架构。

相对于 baseline，我的主要改进可归纳为八点：

1. 将研究对象从单体非线性系统扩展为四车刚性载荷协同运输问题。
2. 建立了载荷中心 Frenet 团队模型，而不是只做单车跟踪。
3. 引入了角点映射、柔性连接误差和载荷受力指标，使“搬运任务”本身进入建模与评价。
4. 将 Adaptive Koopman 的离线升维与在线自适应，任务化落地到车辆团队系统。
5. 在 MPC 回路前增加了通信质量感知一致性层。
6. 显式加入了延迟状态补偿、通信触发约束收紧和退化回退控制。
7. 将安全保护从单一输入裁剪扩展为稳定保护、进度监督、状态裁剪和尾段协同衰减的组合机制。
8. 将实验评价从“跟踪是否成功”扩展为“轨迹、单车误差、连接一致性、载荷力学和求解代价”的证据链。

当前 A1 主任务结果表明，TF12 在同任务 baseline 上实现了：

- 横向 RMSE 从 `0.2075 m` 降至 `0.0513 m`，下降 `75.3%`。
- 平均单步耗时从 `0.2661 s` 降至 `0.2170 s`，下降 `18.4%`。
- 载荷横向峰值力从 `1305.56 N` 降至 `503.04 N`，下降 `61.5%`。
- 连接相对 RMS 均值从 `0.00510` 降至 `0.00241`，下降 `52.7%`。

需要如实指出的是，TF12 的纵向 RMSE 从 `2.8703 m` 上升到 `3.1533 m`，增加 `9.9%`。这意味着它不是“所有指标一起变好”，而是通过更保守的团队协调和安全控制，换来了横向稳定性、受力平顺性与零失败闭环表现。

### 3.2 历史演进分期理解

为了做 PPT 汇报，更适合把上述时间线压缩成四个阶段：

1. **原型验证期（tf3-tf6）**  
   这一阶段的重点是把 baseline 的 Koopman 学习思想迁移到车辆 Frenet 跟踪任务上，先解决“模型能不能学、控制能不能跑”的问题。

2. **工程整合期（tf7-tf10）**  
   这一阶段开始做功能开关、训练测试统一、论文图产出，说明工作目标已经不是单次试验成功，而是走向稳定复现。

3. **协同搬运成型期（tf11）**  
   这一阶段真正把问题从单车控制扩展为四车刚性载荷协同运输，明确了团队建模、受力评估、监督协调等任务属性。

4. **网络韧性提升期（tf12）**  
   这一阶段才形成本文相对于 baseline 的核心创新，即把通信退化直接引入控制闭环，让 Adaptive Koopman 内核能够在多车通信不理想时仍然可用。

## 4. 我相对于 baseline 的核心改进

本节的 baseline 有两层含义：

- **原始 baseline 论文**：即 Singh 等的 Adaptive Koopman Embedding 工作，验证对象是耦合摆、3R 机械臂和平面四旋翼。
- **任务化 baseline（AKE-baseline）**：即在 A1 四车刚性载荷任务上实现的 baseline，对其进行公平对比时保留了 Koopman 与在线自适应核心，但不启用 TF12 的网络韧性模块。

### 4.1 研究对象改了：从单体系统变成协同运输系统

原始 baseline 的主要价值在于证明“离线 Koopman 嵌入 + 在线自适应修正”能够抵抗模型失配。但它的研究对象仍是单体系统，没有显式处理多车协同、刚性耦合和通信退化。

我这里做的第一个根本性修改，是把研究问题改成了四车刚性载荷协同运输，并且让任务目标从单车轨迹跟踪扩展为：

- 团队中心沿参考路径稳定推进。
- 四辆车保持与载荷角点的一致几何关系。
- 车辆之间不要因互相拉扯引发过大横向漂移。
- 载荷的横向力和偏航力矩保持平顺。
- 在时延和丢包存在时仍保持可行求解和安全闭环。

这意味着 TF12 的创新，不是“把 baseline 换个参数继续跑”，而是把 baseline 放进了一个更强耦合、更贴近真实部署的问题设定里。

### 4.2 建模方式改了：从单车状态扩展到载荷中心团队模型

我没有采用“分别对四辆车独立建模再强行拼接”的思路，而是先建立载荷中心 Frenet 团队模型，再通过几何映射把团队中心状态映射到四个角点车辆。

这一步的好处有三点：

1. 把团队整体运动和单车局部误差统一到了同一坐标系里。
2. 能自然引入载荷角点偏移、柔性连接误差和团队一致性约束。
3. 后续 Koopman 升维和 MPC 约束不再只是“单车控制”，而是有了明确的搬运任务语义。

对应地，TF12 里显式建模了：

- 团队中心状态 `x_c=[s_c,e_{y,c},e_{ψ,c},v_{x,c},v_{y,c},r_c]^T`
- 载荷几何参数与角点偏移
- 角点车辆参考状态映射
- 柔性连接误差 `Δs_i, Δe_{y,i}, Δψ_i`
- 载荷受力与角点法向载荷指标

这也是为什么本文实验里不仅比较轨迹误差，还比较载荷横向峰值力、偏航力矩峰值和角点法向载荷波动范围。

### 4.3 离线数据生成改了：从通用系统数据变成团队任务数据

TF12 的离线数据不再是对单体系统的通用训练集，而是围绕 A1 协同搬运任务专门生成的团队级数据。

当前实现中，离线训练数据具有以下特点：

- 共 `720` 条团队轨迹。
- 每条轨迹 `1400` 个状态快照。
- 包含 `5` 组速度与输入边界配置。
- 对 1 车、2 车、3 车、4 车参数变化子集按权重随机采样。
- 采用同一套团队级 Frenet 状态与控制输入定义。

这一步修改的作用在于：在线自适应不需要替代离线模型承担“巨大分布外外推”，而是只需要修正残余模型失配。因此 TF12 对 baseline 的改进，不只是“多加一个在线修正器”，而是把离线数据设计成了真正服务于协同搬运任务的结构化数据。

### 4.4 Koopman 结构改了：从论文思想继承到任务化落地

在学习层面，我保留了 baseline 最核心的思路：离线学习名义 Koopman 升维模型，在线再做局部自适应修正。但我做了两类关键任务化改造。

第一类改造是**升维对象改变**：

- 不再是原始论文中的耦合摆、机械臂、四旋翼。
- 而是四车刚性载荷搬运中的车辆团队状态。

第二类改造是**在线更新策略更保守、更贴近控制部署**：

- 仅使用高置信样本触发在线修正。
- 采用窗口化双线性岭回归，而不是高频率无门槛更新。
- 对更新矩阵进行范数裁剪与稳定性投影。
- 让自适应承担“稳健纠偏”职责，而不是无限制学习。

因此，TF12 在学习层面的定位不是“发明了一个全新的 Koopman 理论”，而是把 Adaptive Koopman 真正嵌入了协同运输场景。

### 4.5 控制栈改了：这是 TF12 相对于 AKE-baseline 的最核心新增

AKE-baseline 与 TF12 的控制骨架大体相同，都保留了：

- 双线性 Koopman 升维
- 在线双线性自适应
- 动态 PPC 软约束
- 误差自适应权重
- 柔性连接一致性

TF12 真正新增的是四个网络韧性模块：

1. **通信质量感知一致性投影**  
   车辆的局部控制命令不再简单聚合，而是先依据链路通信质量做加权融合。通信越差，团队融合越保守。

2. **时延状态补偿**  
   对延迟到达的远端状态，不直接当作实时值使用，而是按当前速度和角速度向前预测。

3. **通信触发约束收紧**  
   当全局通信质量下降时，输入边界自动收紧，使控制动作更保守，从而避免网络退化时的过激控制。

4. **退化回退控制**  
   当通信质量低于阈值或丢包比例过高时，团队控制会混入保守安全控制器，而不是继续完全依赖名义求解结果。

这四个模块串起来，才构成 TF12 的核心贡献。单看其中任何一个模块，它都不一定是领域内最新奇的算法；但把它们系统性地嵌进 Adaptive Koopman-MPC 协同运输闭环里，就是 TF12 的真正创新点。

### 4.6 安全保护改了：从输入限幅变成多层保护栈

为了支撑网络退化下的稳定闭环，TF12 在基础约束之外，还设计了多层安全保护：

1. **紧急稳定保护**  
   当横向误差或航向误差越界时，附加稳定转角并增强制动。

2. **进度监督与状态裁剪**  
   防止路径进度回退，同时限制关键状态的可接受范围。

3. **团队协同尾段衰减**  
   在任务后段逐步减弱协同校正，降低终点附近因“互相拉拽”导致的波动。

从审稿视角看，这些内容更多属于“工程完整性增强”而不是最核心的算法新颖性，但它们对提升论文说服力非常重要，因为它们解释了系统为什么在网络退化下还能稳定运行。

### 4.7 评价体系改了：从单一误差转为任务级证据链

原始 baseline 更关注控制误差是否下降，而 TF12 的评价体系更贴近协同搬运任务本身。

现在的评价链条包括：

- 团队全路径完成率
- 求解成功率
- 团队横向/纵向误差
- 单车误差
- 连接一致性指标
- 载荷纵向力、横向力、偏航力矩
- 角点法向载荷范围
- 计算时间

这一步的意义在于，TF12 的收益不再只能表述为“跟踪更好”，而可以更有说服力地表述为“搬运更稳、拉扯更小、载荷更平顺、闭环更可靠”。

### 5.3 如何解读这些结果

结果最值得强调的不是“所有指标都赢”，而是以下三点：

1. **横向稳定性显著增强**  
   这是网络韧性模块最直接的收益，因为通信质量感知一致性和时延补偿最直接抑制的就是团队成员之间的横向相互冲突。

2. **载荷冲击显著下降**  
   横向峰值力下降 `61.5%`、偏航力矩峰值下降 `55.6%`，说明 TF12 不是仅仅把轨迹画得更好看，而是把“搬运动作”本身做平顺了。

3. **纵向推进更保守**  
   纵向 RMSE 增加 `9.9%`，说明 TF12 更偏向稳态和安全，而不是追求最快推进。这个 trade-off 必须在汇报和论文里主动说明，否则容易被误解为结果不一致。

## 6. 论文写作层面的历史修改

除了方法本身，这次工作在论文组织上也经历了明显重构。可以把这部分单独当成一条“历史修改线”。

### 6.1 初版写法的主要问题

初版中文导出版虽然已经把主要模块写进去，但有两个关键问题：

1. 对比口径不够严格，容易被读者误解为“TF12 与历史版本号比较”，而不是与任务化 baseline 比较。
2. 引言、方法和实验之间的一一对应关系不够强，文章更像“先把功能写上去”，而不是“按研究问题逐层展开”。

### 6.2 后续重构的主要动作

后续对中文稿做了以下实质性重写：

1. **纠正比较对象**

### 6.3 现在这版文稿的优势

## 7. 从一区 top 审稿人的视角看，这些修改值不值得写成论文

### 7.1 审稿人最可能认可的地方

1. **问题升级是真实的**  
   这项工作不是把 Adaptive Koopman baseline 在原算例上做微调，而是把它推进到了多车协同运输和通信退化场景里。

2. **创新点是成体系的**  
   通信质量感知一致性、时延补偿、约束收紧和退化回退之间是闭环关系，不是随手堆叠的四个补丁。

3. **实验指标贴合任务**  
   受力、连接一致性、角点载荷波动这些指标非常契合“协同搬运”这个问题，能证明工作理解了任务本质。

4. **对比口径更公平**  
   把 baseline 定义为 AKE-baseline，而不是历史版本号比较，有助于提升论文的学术严谨性。

### 7.2 审稿人最可能追问的地方

1. **Koopman 学习层面的理论新颖性有限**  
   学习内核更多是继承和任务化落地，最大的创新在系统架构层，而不是 Koopman 理论本身。

2. **需要更强的 ablation**  
   审稿人很可能会问：如果只加通信质量感知一致性，不加时延补偿，会怎样；如果只加约束收紧，不加回退，会怎样。

3. **需要更清晰的稳定性或可行性说明**  
   尤其是退化回退和约束收紧触发时，递归可行性、平滑性和保守性需要更完整的解释。

4. **要主动解释纵向 RMSE 变差**  
   这个现象不能回避，必须解释为安全性和团队稳定性优先下的控制 trade-off。

### 7.3 审稿结论倾向

如果把这项工作写成“我们在 baseline 上又加了几个功能”，那它容易被降级看作工程叠加。  
但如果把它写成“Adaptive Koopman 如何被扩展为 network-resilient cooperative transport control”，并用完整对比和证据链支撑，那么它对一区交叉类期刊是有竞争力的。
