当前 `parallel_fd_backend.py` 使用ProcessPoolExecutor(max_workers=8)，调用NumPy的rollout_step；预测模型为NumPy，QP为SciPy稀疏矩阵和当前OSQP接口。不是加一个device='cuda'就会迁移。

每次线性化：34维增广状态（30状态+4实际转角）、8维控制，中心差分84个扰动rollout，加1个名义rollout共85；逐预测步重算20次，即约1700次20ms预测传播，每次10个2ms RK4更新，约68000次RK4右端计算量（未含其他特征/约束及验证）。瓶颈与此前profile的动力学线性化94%—95%一致，首先应迁移这一层，而不是先换QP求解器。

## 3. 推荐架构：GPU批量预测差分，CPU保持真实植物和QP

首版隔离新增 `gpu_port/`，不覆盖已冻结controller/plant。保持N=20、FD步长、逐步雅可比、权重、转角/受力界及信息边界，使用float64；不同时引入float32、AMP、自动微分或改变积分器。

- `physics_torch.py`：把预测rollout所调用的转向指数更新/限幅、车辆与货物动力学、连接器分段律、载荷转移、轮胎及RK4逐函数改为支持批维的Torch实现。参数为设备常驻tensor，不在内循环调用numpy或CPU回调。验证clip/where分支及无效分支除零，不因向量化计算原本未求值分支而引入NaN。
- `rollout_batch.py`：输入Z[B,34]、U[B,8]，每项独立执行同一10次2ms执行器+RK4；返回[B,34]。先保证数学/分支语义，再优化kernel和编译。
- `fd_backend.py`：按旧顺序构造名义+正负扰动，批量送GPU；固定索引重构A[34,34]、B[34,8]。同一个预测步84个扰动可并行；20个预测步依赖前步名义状态，首版不能把它们当20个独立初态直接并行。
- QP组装/OSQP与非线性硬门暂留CPU，真实植物及event_substep保留原实现；GPU只服务预测线性化。单GPU单进程，去掉此路径上的8个CPU进程，不开8个CUDA上下文互抢资源。

下面只是接口骨架，不是可直接替换现有程序的实现；其中physics必须按上述完整实现：

```python
def linearize_cuda(z, u, params, state_steps, control_steps):
    # 所有输入显式float64、cuda；顺序：nominal, z0+/-,...,z33+/-,u0+/-,...,u7+/-
    Z = z[None, :].repeat(85, 1)
    U = u[None, :].repeat(85, 1)
    for j in range(34):
        Z[1 + 2*j, j] += state_steps[j]
        Z[2 + 2*j, j] -= state_steps[j]
    for j in range(8):
        U[69 + 2*j, j] += control_steps[j]
        U[70 + 2*j, j] -= control_steps[j]
    Y = rollout_batch_torch(Z, U, params)  # 待实现；不能调用NumPy的rollout_step
    A = ((Y[1:69:2] - Y[2:69:2]) / (2*state_steps[:, None])).T
    B = ((Y[69:85:2] - Y[70:85:2]) / (2*control_steps[:, None])).T
    return Y[0], A, B
```

生产版应使用批量索引构造扰动，避免上面演示的逐元素GPU赋值开销；名义状态尽量留设备，CPU仅在组装需要时一次取回A/B等块。计时必须在GPU操作前后同步，并分别记录预热/编译、内核、传输、QP/复核及端到端耗时，不能只报异步kernel发射时间。

## 4. GPU资格分层，不自动要求“跨CPU/GPU逐位完全一致”

PyTorch官方说明：相同输入的浮点结果不保证跨CPU/GPU或批量/逐项计算逐位一致。因此原串行/CPU并行的bitwise门不能直接冒充GPU的数值等价门；须独立登记数值后端及新资格合同，原CPU PASS/失败全部保留。[官方数值精度说明](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html)

| 阶段 | 使用证据与输出 | 通过后允许什么 |
|---|---|---|
| G0环境 | 设备/版本/源码清单、CUDA float64与内存检查 | 固定输入测试，不开闭环 |
| G1物理函数 | 当前合法开发数据中直线、入弯、有力峰、限幅、近间隙边界、晚段共6类固定样本；对比rhs、一次RK4、20ms rollout | 语义一致、无新增非有限值后才测Jacobian |
| G2差分/QP | 固定相同z/u/previous_u/refs；CPU/GPU f0/A/B、P/q/Aqp/l/u、首控制、CPU非线性复核 | 资格与成本报告，不能声称R4已通过 |
| G3短窗 | 完整初态/记忆可恢复后，分别做有力/转向限幅/晚段短窗，双方对照与原硬门 | 有界闭环验证；本次尚未授权启动 |
| G4完整验证 | 依据CPU/GPU差异决定新版本2/1/0.5ms验证与后续R4计划 | 必须重新冻结，禁止拼入2200周期前缀直接宣布完成 |

G1/G2误差必须逐字段带单位，用 `abs_error/(atol+rtol*abs(reference))` 报告，并同时给绝对最大/RMS/最差样本。阈值在运行GPU前按CPU重复误差、原差分步长及物理分辨率登记；不能把统一默认allclose当科学标准。中心差分会把函数误差按1/h放大，h含1e-6，必须同时检验导数和首控制，单次rollout接近不充分。原硬物理约束、完成条件和注册数值门不得放宽。

若出现明显分支/控制/约束活跃变化，登记新数值实现甚至新算法候选，不能宣称已等价。自动微分可另作后续方案，但对饱和/间隙/载荷切换的导数定义可能与中心差分不同，不与首版GPU移植混在一起。

性能目标是端到端优于当前约13.91s/步，争取原5s预算；GPU能否达到须实测。85个小规模系统、许多小kernel、float64和CPU/GPU往返均可能限制加速；有CUDA不保证更快。若G2端到端无收益，停止长试，分析kernel融合/编译或CPU编译优化，不盲目重跑整条。
